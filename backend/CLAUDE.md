## What this is

The Finance CRM backend — a migration of the legacy PHP CRM (`../old-php-files/`, the internal staff-facing CodeIgniter install) to NestJS. Scope is the **internal CRM + its automation** — explicitly excludes the legacy app's separate customer-facing `api/` install (Android/iOS/website) and the marketing site/blog/news.

`backend/` is a **bun workspaces monorepo** with 5 deployable units, not a single NestJS app. See `docs/TODO.md` for what's still open and `docs/COMPLETED.md` for the full migration history.

## Layout

Every service/package is a direct child of the repo root (no `apps/`/`packages/` wrapper):

```
core-api/            # loan-lifecycle CRUD/workflow: leads, CAM, BRE, disbursal, collection,
                     # verification, feedback, users/roles/auth, company, geography, audit,
                     # menu/permissions, search. Public HTTP API, JWT-guarded by default.
reporting-api/       # MIS reports + CSV exports. Read-only, permission-gated per report/export type.
integrations-api/    # every third-party vendor call (bureau/eKYC/eSign/eNACH/face-match, payment
                     # gateways, SMS/email). One module per vendor, each an adapter gated behind
                     # env-var credentials — functional the moment real keys are supplied, never
                     # mocked. Finbox/Adjust/AppsFlyer/TinyURL and the whole WhatsApp category
                     # were removed on client instruction (docs/EXCLUDED.md) — don't re-add one
                     # without asking.
automation-worker/   # cron/background jobs (allocation, reminders, campaigns, doc housekeeping,
                     # attribution pushes). No public routes. Calls into core-api/integrations-api
                     # over HTTP using env-var service URLs.
gateway/             # nginx reverse proxy, pure routing/CORS/cookie-forwarding — no app code here.
database/            # @finance-crm/database — every TypeORM entity (grouped by domain folder) + a shared
                     # DataSource factory + migrations. Every service imports only the entities it uses.
common/              # @finance-crm/common — JwtAuthGuard/RolesGuard/@Public/@Roles/@CurrentUser, pagination
                     # DTOs, findOrFail(), the file-storage adapter, the PDF library, the pluggable
                     # job-runner interface.
docs/                # TODO.md (open items only, kept small), COMPLETED.md (full history of
                     # everything already done), DETAILS.md (setup/architecture detail),
                     # DEPLOYMENT.md (AWS runbook).
```

## Architecture decisions (don't relitigate these without asking)

- **Service split — 5 deployable units**: `core-api` (all loan-lifecycle CRUD/workflow + audit + menu/permissions + search), `reporting-api` (MIS reports + CSV exports), `integrations-api` (every third-party vendor call, one module per vendor), `automation-worker` (cron/background jobs, no public HTTP routes), `gateway` (nginx reverse proxy, routing/CORS/cookie forwarding only, no business logic). One internal ALB in front of per-service EC2 instances in production, path/host-based routing rules per service (see `docs/DEPLOYMENT.md`).
- **Shared database, service-owned modules** — all services connect to the same MySQL DB; there is no per-service database or event-sourcing sync. Cross-entity joins (Lead → CAM → BRE → Loan → Collection) work exactly as they do in a single app; services just each register a subset of `@finance-crm/database`'s entities via `TypeOrmModule.forFeature`. **Gotcha**: if a module registers an entity that has `@ManyToOne` relations (e.g. `Lead` → `Company`/`Product`/`State`/`City`/`Branch`/`MasterStatus`/`RejectionReason`/`User`, or `User` → `Company`/`Product`), every one of those related entities must *also* be registered via `forFeature` somewhere in the same app, or TypeORM's `autoLoadEntities` fails at boot with `Entity metadata for X#y was not found` — it only collects entities that some module explicitly registers, not everything reachable via decorators. Each service that touches `Lead`/`User` should have one small shared module (see `core-api`'s `CommonModule`, `integrations-api`'s `common/common.module.ts`) registering that full transitively-referenced set once, and every feature module imports it instead of re-registering `Lead`/`User` piecemeal.
- **Env-var-driven service URLs, always** — never hardcode `http://core-api:3000`-style hostnames. Every inter-service call reads its target from an env var (`CORE_API_URL`, `INTEGRATIONS_API_URL`, etc.). This is what lets the same code run under `docker-compose` (env var = compose service name) or across separate EC2 instances behind an internal ALB in production (env var = ALB DNS name / path) with zero code changes.
- **Job execution is pluggable, not hardcoded** — `@finance-crm/common`'s `JobRunnerModule` exports a `JOB_RUNNER` DI token implementing `JobRunner.schedule(name, cronExpression, handler)`. Defaults to `InProcessJobRunner` (`@nestjs/schedule`'s `SchedulerRegistry` + dynamically-created `CronJob`s — not the static `@Cron()` decorator, since jobs are registered by name/expression at runtime); auto-upgrades to `BullMqJobRunner` (Redis-backed, retries, concurrency control, safe across multiple `automation-worker` replicas) when `REDIS_URL` is configured — same factory-provider toggle pattern as `StorageModule`'s local/S3 switch. Don't hardcode a choice in a new cron job — inject `JOB_RUNNER` and call `.schedule()`. `automation-worker` reads/writes the shared database directly via TypeORM (`CommonModule`/`ALL_ENTITIES`, same pattern as `reporting-api`) rather than through `core-api`'s HTTP API — `core-api`'s routes are all JWT-per-user-guarded (staff sessions), and going through a real user-facing API for cron/background work would mean impersonating a user that doesn't exist, so direct DB access is the pragmatic default (also matches how the legacy PHP cron scripts worked). It still calls `integrations-api` over real HTTP (`IntegrationsApiClient`, `INTEGRATIONS_API_URL`, both from `@finance-crm/common`) for vendor actions (SMS/email/WhatsApp/attribution) — that service's adapters are the actual point of the call.
- **Service-to-service calls are HMAC-signed, not unauthenticated** — the only real inter-service HTTP traffic in this system (`core-api`/`automation-worker` calling `integrations-api`) is signed via `@finance-crm/common`'s `internal-service-auth.util.ts` (`INTERNAL_SERVICE_SECRET`, shared across the 3 services involved) and verified by `JwtAuthGuard`'s internal-request path — a second, parallel path alongside the normal cookie-JWT check, not a bypass of it. A server-to-server axios call never carries a session cookie, so without this every non-`@Public()` `integrations-api` route would 401 it; `@finance-crm/common`'s `IntegrationsApiClient` is the only sanctioned way to make one of these calls — don't hand-roll a second unsigned HTTP client for a new inter-service call.
- **Config/secrets resolution is a 2-stage chain over `.env`, restart-only** — every one of the 4 NestJS services bootstraps `ConfigModule.forRoot({ load: [awsSsmLoader, awsSecretsLoader] })` (`@finance-crm/common`'s `config/aws-ssm-loader.ts` / `config/aws-secrets-loader.ts`). Both loaders use the AWS SDK's default credential provider chain (IAM instance-role, no explicit access keys — same pattern as `S3StorageAdapter`) and both no-op to `{}` (never throw) when their env var (`AWS_SSM_PARAMETER_PATH` / `AWS_SECRETS_MANAGER_SECRET_NAME`) is unset or the call fails, so local dev with no AWS access falls straight through. Values returned by `load` factories take precedence over `.env`/`process.env` in `ConfigService.get()` (NestJS internal-config-before-process-env resolution order) — later entries in the `load` array win on a key clash, so Secrets Manager is listed after SSM. **Nothing is read from the database.** A third stage briefly existed — `CrmSettingsService` over the `crm_settings` table, with cron-job schedules as its only consumer — and was removed on 2026-08-07 by client instruction; `ConfigurableJobRunner` now resolves a job's timing from the `CRON_<NAME>` env var or the job's hardcoded default, nothing else. The service, entity and table still exist with zero consumers (see `docs/TODO.md`). All of this is restart-only by design — no polling, a changed secret/parameter takes effect on next boot, same as changing an env var. Don't reintroduce a DB-backed config stage, and don't retrofit the ~130 existing `config.get()` call sites onto one, without a new explicit decision.
- **The vendor list is a client-owned decision, not a developer one (2026-08-07)** — the client supplied a definitive keep-list (Surepass, CRIF direct, Signzy, Digitap, Google Maps, Razorpay, ICICI, Vapio, RUNO, ZeptoMail, plus CartBI and the SES/SMTP senders they confirmed separately) and Finbox, Adjust, AppsFlyer, TinyURL and the entire WhatsApp category were removed against it (`docs/EXCLUDED.md`, `docs/COMPLETED.md` Task #146). Credeau was on that first keep-list, removed in the same pass, then restored at the client's request the same day (Task #147) — and finally removed for good once the client separately confirmed it, and the lead-allocation cron band that shared its name, weren't used at all (Task #158). Removals are code-only: **every existing table and row is preserved** — nothing is ever dropped — and provider *enum values* stay (they decode numeric ids on existing rows). `m1.sql` still creates the removed vendors' *legacy* log tables (`api_finbox_device_connect_logs`, `api_appsflyer_push_events`, `api_url_shortener_logs`), since those are real tables an environment may already hold rows in; Credeau's own legacy table (`api_credeau_log`) is created by `init.sql`, untouched for the same reason. The one exception, on client instruction (2026-08-07): `m1.sql` no longer creates `whatsapp_logs`, which was never legacy — it was a NEW table this rewrite invented for a module that no longer exists, so not creating an empty table for a module nobody has isn't a removal of anything. Legacy `api_whatsapp_logs` is created by `init.sql` and untouched. Don't add a new vendor module, and don't resurrect a removed one, without an explicit client decision.
- **Third-party integrations are real adapters, not mocks** — `integrations-api` modules match each vendor's actual request/response shape and error handling. They read credentials from env vars and simply won't function until real keys are supplied — that's expected, not a bug to "fix" with a mock.
- **File storage and PDF generation are shared libraries, not services** — no external credentials needed for PDF rendering, and giving it its own service would just add a network hop for a synchronous user action (e.g. "download sanction letter"). Storage defaults to local disk, S3 is a drop-in behind the same interface (mirrors the legacy `LMS_DOC_S3_FLAG` toggle).
- **No raw string-concatenated SQL** — the legacy Search module had a real SQL-injection bug from building queries via string concatenation. Every port uses parameterized TypeORM queries. This applies everywhere, not just Search.
- **Never add a column to model a relation legacy doesn't already have** — if two legacy tables are already linked through an existing column that isn't a formal FK (e.g. `leads.customer_id` ↔ `cif_customer.cif_number`, both varchar; `collection.loan_no` ↔ `loan.loan_no`), express that relation at the entity level with `@ManyToOne(...) @JoinColumn({ name: '<existing column>', referencedColumnName: '<property>' })` — never by adding a new FK column. This is additive-migration-column discipline applied to relations, not just plain columns; see `docs/SCHEMA-MAP.md` and `database/src/additive-schema-changes.ts` for the column-addition rule this extends.
- **Schema migrations are plain numbered `.sql` files, not TypeORM (2026-08-05)** — `database/sql-migrations/init.sql` (the 149-table legacy baseline, structure only) plus `mN.sql`/`mN.down.sql` pairs (`m1.sql` and `m2.sql` today), run via `bun run migrate` (`database/src/run-sql-migrations.ts`: `--init`, `--mN` = m1..mN, `--mA-mB` = an explicit range, no flags defaults to `--m1`). Replaces the old single-hand-maintained TypeORM migration file entirely — deliberately, so every file here is ALSO valid to paste straight into phpMyAdmin or any other MySQL client, since some environments (shared hosting, UAT) may only have that kind of access, not a direct DB connection this repo's tooling can reach.
  - **Every item in an `mN.sql` is idempotent** — real environments can be in different starting states (UAT was found missing a primary key prod/dev already have), so every item checks `information_schema` before acting and no-ops if its target already exists, rather than assuming a specific starting shape. `CREATE TABLE`/`DROP TABLE ... IF [NOT] EXISTS` are native and portable; `ADD COLUMN`/`ADD PRIMARY KEY`/`ADD CONSTRAINT` are NOT — confirmed real MySQL (unlike MariaDB) rejects the `ADD COLUMN IF NOT EXISTS` shorthand outright — so those build the real statement as dynamic SQL (`SET`/`PREPARE`/`EXECUTE`/`DEALLOCATE`) gated on an `information_schema` check. Each item is one blank-line-separated block led by a `-- TARGET: <KIND> <descriptor>` comment the runner parses to know what to check.
  - **Failure-recovery is a best-effort revert**, since MySQL auto-commits every DDL statement even inside a transaction — there is no real `ROLLBACK` for schema changes. Each `mN.sql` must have a `mN.down.sql` with the exact same block count in exactly reversed order (enforced by convention, not tooling — keep new pairs in lockstep by hand, and equally idempotent). Before running a file, the runner snapshots whether each block's target already existed; on a later failure it reverts every block THIS RUN actually changed, in reverse, but skips ones whose target predates this invocation — otherwise a no-op'd block (because that environment already had it) would get wrongly undone. Verified end-to-end: a column added manually before a run started survived a later mid-file failure's revert untouched, while everything the run itself added was cleanly removed.
  - No tracking table records what's been applied where — the operator passes the right `--mN`/`--mA-mB` range; a fully-idempotent file can safely be re-run against the same database with no effect (confirmed), so accidentally re-running is harmless, just redundant.
- **IaC scope: Dockerfiles + `docker-compose.yml` + env-var contract only, no Terraform** — no cloud credentials available in this environment to write/apply IaC against. `docs/DEPLOYMENT.md` is instead a step-by-step manual AWS runbook (VPC/subnets, EC2 per service, internal ALB, RDS, S3, security groups, env-var checklist) detailed enough to execute by hand in the AWS console/CLI.
- **Security posture set by the 2026-08-06 full security review (`docs/COMPLETED.md` Tasks #142-#145)** — five rules that are load-bearing, not stylistic:
  - **Every inbound vendor webhook must authenticate, and must fail closed.** Razorpay uses its own `x-razorpay-signature` HMAC and ICICI UPI uses RSA decryption of the body; the four that carry no signature of their own (Signzy video-KYC/eSign, CartBI bank-analysis/account-aggregator) go through `integrations-api`'s `VendorCallbackTokenGuard` (`VENDOR_CALLBACK_TOKEN`). That guard **rejects every request while the env var is unset** — don't "fix" that by making it skip when unconfigured, which is exactly the bypass it exists to close. A callback must also never take the lead it acts on from its own payload: correlate a vendor-supplied `requestId` back to the log row written when *we* made the outbound call (see `VideoKycCallbackController`, which had this exact hole).
  - **Anything rendered by the PDF pipeline must escape through `@finance-crm/common`'s `escapeHtml`.** The templates go through headless Chrome, so an unescaped DB string is server-side script execution inside the VPC against a legally binding document, not a cosmetic bug. There is exactly one `escapeHtml` (`common/src/html/`) — don't add a ninth local copy, which is what this replaced. The renderer keeps Chrome's sandbox (all four Dockerfiles run as a non-root `app` user specifically so it can) and blocks every non-`data:` request; don't reintroduce `--no-sandbox`.
  - **A `@Public()` route must never return an entity with relations attached.** `ClassSerializerInterceptor` only strips `@Exclude()` fields, and `Lead` has none — returning a saved `CustomerFeedback` leaked borrower mobile/email/PAN to unauthenticated callers. Return an explicit narrow shape (`{ id }`).
  - **An unauthenticated endpoint must not report *why* it rejected something.** The public UPI callback echoing its distinct RSA-padding/parse failures back was a working Bleichenbacher oracle. One constant rejection message to the caller, detail to the log.
  - **Secrets are validated at boot, not just read.** `@finance-crm/common`'s `assertStrongSecrets()` runs in all three HTTP services' `bootstrap()` and refuses to start on a placeholder or sub-32-char `JWT_ACCESS_SECRET`/`INTERNAL_SERVICE_SECRET` (warning only under `NODE_ENV=development`). Add any new shared secret to that call rather than trusting `getOrThrow`, which only checks presence.
  - Rate limiting exists (`@nestjs/throttler` in `core-api`/`integrations-api`, with tight per-handler `@Throttle` budgets on every credential route) — put a budget on any new unauthenticated route. `helmet()` and `trust proxy` are set in all three `main.ts` files; Swagger is behind `SWAGGER_ENABLED` because its handlers bypass the global guard.
  - **Still open, deliberately:** there is no per-lead authorization model and `menu_permissions` is enforced nowhere. That needs a client decision, not a guess — see `docs/TODO.md`. Don't invent a role→lead-stage read policy without one.

- **Monorepo tooling: bun workspaces only, no Nx/Turborepo** — 5 deployable units doesn't justify that overhead.
- **Fresh rewrite against the legacy schema (2026-08-01, `docs/COMPLETED.md` Tasks #105-#110)** — the entire service layer (`database`, `common`, and all 5 services) was rebuilt from scratch against the real legacy MySQL schema rather than continuing to extend the prior build. The prior backend is archived at `backend/old/` (gitignored, kept on disk as a porting reference — read it for business logic, but every entity/table/column reference in it must be re-verified against `@finance-crm/database`'s current entities before reuse, since it predates the schema adoption). This rewrite is complete; don't restart it again without a new, equally explicit decision.

## Conventions established across all services

- `findOrFail<T>(repository, id, label)` (`@finance-crm/common`) for every FK-or-404 lookup — don't reinvent per-entity helpers.
- Thin controllers, business logic in services. `UpdateXDto extends PartialType(CreateXDto)` via `@nestjs/mapped-types`.
- List endpoints take a `ListXQueryDto extends PaginationQueryDto` and return `PaginatedResult<T>` (`@finance-crm/common`).
- Every route is guarded by default (global `JwtAuthGuard` + `RolesGuard`, registered once in `core-api`'s `AuthModule` — other services apply the same guards from `@finance-crm/common`). Mark a handler `@Public()` only for genuinely pre-auth routes. Admin-only resources get `@Roles('SA','CA')` at the controller level.
- Workflow-changing actions (status transitions, assignments, approvals) write to the relevant audit-trail entity (e.g. `LeadFollowup`) — don't silently mutate state without a trail entry if one exists for that entity.
- Biome for lint/format (not eslint/prettier) — `unsafeParameterDecoratorsEnabled: true` is required in `biome.json` for NestJS's constructor-injection pattern to parse; if that setting goes missing, every service's DI constructors will throw parse errors, not something to "fix" in the code.
- **`ConfigService.get<T>()` never casts** — the generic type parameter is a type hint only; every env var is a string at runtime. Arithmetic (`x * 1000`) auto-coerces so it's harmless there, but passing the raw value straight into a library option is not: this actually broke JWT expiry (`expiresIn: "900"` got misparsed by the `ms` package as ~0.9s, not 900s) and bcrypt salt rounds (a string `saltOrRounds` is treated as a literal salt and throws) until both were wrapped in `Number(...)`. Always wrap `config.get(...)` in `Number(...)` when the value feeds a non-arithmetic API.
- Husky pre-commit runs `bun run lint && bun run format && bun run typecheck` — commit messages must follow Conventional Commits (`<type>(<scope>): <subject>`).
